## 2. Целевая архитектура

### 2.1 Принцип

Разделяем то, что сейчас смешано в одном вызове Gemini, на три чётко разных механизма:

1. Скриптовый контент ноды.
2. Свободная генерация ответа клиенту.
3. Переход между шагами (routing).

### 2.2 Новая схема dialogue_flow

Фаза B использует узлы со структурой:
- `message_type`: `script` или `dynamic`
- `script_parts`: массив строк для скриптовых сообщений
- `instruction`: текст для динамической генерации
- `extract_fields`: массив имён полей, которые нужно извлекать из сообщения клиента на этом шаге
- `transitions`: массив переходов `{ condition, target }`
- `fallback_condition`: условие fallback-перехода, по умолчанию `no_match`
- `fallback_target`: целевой узел fallback-перехода, по умолчанию id текущего узла
- `max_retries_before_handoff`: число повторов перед handoff

Стандартный набор условий переходов:
- `answers_received`
- `yes`
- `no`
- `unclear`
- `price_asked`
- `price_presented`
- `values_presented`
- `purchase_confirmed`
- `objection_resolved`
- `objection_raised`
- `default`
- `no_match`

Правила:
- `default` используется для безусловных переходов без вызова классификатора маршрутизации.
- `no_match` используется как fallback, если ни одно условие не подошло.
- `extract_fields` заполняется вручную по смыслу узла, а не оставляется пустым молча.

### 2.3 Новые таблицы БД

По состоянию на текущий код и миграции после 2026-07-04 существует одна новая миграция Phase B, добавляющая именно те таблицы, которые нужны для персистентного состояния воронки:

- db/migrations/20260710120000_funnel_phase_b_state_tables.sql
  - lead_funnel_state
    - id, lead_id, agent_id, current_node_id, status, retry_count, last_transition_at, created_at, updated_at
    - уникальность по (lead_id, agent_id)
  - funnel_transitions_log
    - id, lead_id, agent_id, from_node_id, to_node_id, condition, classification_confidence, metadata, created_at
  - RPC upsert_lead_funnel_state
    - принимает current-node/status/retry/no-match/time и используется для атомарного обновления state
  - RLS включён и для обеих таблиц созданы политики для org members

Больше новых таблиц Phase B после 2026-07-04 в репозитории нет.

### 2.4 Два вызова Gemini вместо одного смешанного

Обязательное условие реализации Phase B:
- Если у узла есть единственный переход с `condition: "default"`, то вызов B (routing-классификатор) не должен выполняться.
- В этом случае переход должен происходить напрямую в целевой узел `target` без дополнительной классификации.
- Это требование должно быть зафиксировано в реализации Phase B, а не только в спецификации.

## 3. Что НЕЛЬЗЯ делать при реализации

Ниже — ограничения, которые должны быть зафиксированы в спецификации и не нарушаться при дальнейшей разработке.

- Нельзя смешивать в одном вызове Gemini три задачи: скриптовый контент узла, свободную генерацию ответа клиенту и routing между узлами. В уже написанном коде это уже разделено: в runAgentTurn есть отдельный script-path для узлов с message_type=script, а routing вынесен в applyFunnelRouting.
- Нельзя хранить состояние воронки только в неструктурированном поле leads.attributes.current_node_id и считать это полноценной моделью. Для Phase B нужны durable state + retry + transition log. В коде это уже частично реализовано через lead_funnel_state и funnel_transitions_log.
- Нельзя добавлять новые таблицы без RLS. В миграции 20260710120000 RLS уже включён и для обеих таблиц созданы политики.
- Нельзя хранить секреты в коде. В Phase B-части кода не найдено явных hardcoded credentials; используются переменные окружения (например, NEXT_PUBLIC_SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY).
- Нельзя оставлять несовпадение между вызовом RPC и схемой БД. В текущем коде lib/funnel/routing.ts вызывает upsert_lead_funnel_state с параметрами p_pending_script_node_id / p_pending_script_reply, но миграция 20260710120000 создала старую версию функции без этих аргументов. Это официальный риск, который нужно учитывать при ревью.

## 4. Фазы реализации (строго по порядку, подтверждение между фазами)

### Фаза A — Хотфикс без изменения структуры воронки (можно выкатить быстро)

1. Пофиксить model на gemini-2.5-flash у всех агентов с некорректным значением.
2. Отключить style-валидатор для узлов текущего dialogue_flow, если их контент отправляется как прямой скрипт.
3. Изменить логику фолбэка: если raw ответ не пустой и не является нарушением, приводящим к небезопасному/некорректному контенту — отправлять raw, а не заглушку.
4. Добавить поле current_node_id в leads.attributes как временное решение персистентности.

### Фаза B — Полная FSM-архитектура

По факту уже написанного кода, Phase B должна была включать следующее:

- переход от линейного dialogue_flow к явной FSM-модели узлов;
- у каждого узла есть structured поля: message_type (script/dynamic), script_parts, instruction, extract_fields, transitions, fallback_condition/fallback_target, max_retries_before_handoff;
- script-узлы должны отдаваться как готовый текст без вызова Gemini, а dynamic-узлы — через генерацию;
- переходы между узлами должны быть частью графа, а не решаться LLM по свободному тексту;
- для переходов нужен отдельный routing-классификатор, который возвращает condition/confidence и применяется в applyFunnelRouting;
- если у узла ровно один переход с condition=default, переход должен выполняться напрямую, без дополнительной классификации;
- состояние шага должно сохраняться в lead_funnel_state, а лог переходов — в funnel_transitions_log;
- миграция старого dialogue_flow в новую структуру должна происходить через lib/funnel/dialogue-flow-migration.ts;
- инструменты advanceFunnelStep / redirectToOperator / searchKnowledgeBase остаются частью runtime, но не заменяют явный routing-граф.

То есть Phase B в коде уже выглядит как не просто "ещё одна фича", а как отдельная FSM-архитектура для диалогов, где контент, генерация и routing разделены по разным слоям.

## 5. Скрипт миграции старого dialogue_flow

В репозитории уже есть два скрипта, и текст раздела должен описывать именно их.

- scripts/prepare-dialogue-flow-migration.ts
  - читает всех агентов с non-null dialogue_flow;
  - запускает convertDialogueFlowForMigration для каждого;
  - генерирует preview markdown в docs/dialogue_flow_migration_preview.md;
  - генерирует review markdown в docs/migration_review_needed.md;
  - это шаг подготовки и review, а не применение к БД.

- scripts/apply-dialogue-flow-migration.ts
  - берёт жёстко заданный список target-agent-id;
  - создаёт backup snapshot в table agent_versions;
  - обновляет dialogue_flow у выбранных агентов на converted flow;
  - это реальное применение миграции к БД.

Ожидаемый порядок запуска: prepare → review → apply.

Важно: в текущем коде нет режима dry-run для apply-скрипта; он сразу пишет в БД. Поэтому для безопасной выкатки нужен отдельный review/preview-шаг и ручное подтверждение до apply.
