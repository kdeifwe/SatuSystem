# Frontend

## Стек и базовые правила

- Next.js App Router. Server Components по умолчанию; Client Component — только там, где реально нужна интерактивность (drag-n-drop канбана, чат, графики, формы с состоянием).
- Realtime — через подписку на Supabase Realtime (`messages`, `leads`), не через polling.
- Каждый крупный экран соответствует ровно одному модулю из `/docs/SPEC.md` раздела 6. Не придумывай новые разделы UI, которых нет в списке модулей — если кажется, что чего-то не хватает, сначала обнови SPEC.md, потом код.

## Права доступа — UI и API одновременно

Любой элемент интерфейса, запускающий привилегированное действие (рассылка, смена статуса, удаление), должен:
1. Скрываться в UI, если у `org_members.section_permissions` участника нет доступа к разделу.
2. **И** проверяться на уровне API/server action — скрытая кнопка не защита, если эндпоинт всё равно выполнит запрос при прямом вызове.

Это не опционально — это пункт 9.8 в чек-листе SPEC.md, его будут проверять.

## Состояния загрузки и ошибок

Любой компонент, получающий данные асинхронно, обязан иметь явные состояния loading/error/empty. Тихий провал (пустой экран без объяснения) — баг, а не "так получилось".

## Формы

Одна Zod-схема на форму, используемая и на клиенте (мгновенная валидация), и на сервере (server action) — не дублируй правила валидации вручную в двух местах.

## Sandbox vs реальные диалоги

UI Sandbox (раздел "Тестирование" из SPEC.md) должен визуально и по данным быть полностью отделён от реальных диалогов с клиентами — другая таблица/флаг, не просто другой фильтр на тех же данных. Иначе тестовые сообщения попадут в статистику и канбан.
