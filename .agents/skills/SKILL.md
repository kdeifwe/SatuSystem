# Backend

## Правила, которые нельзя нарушать

1. **Webhook отвечает 200 OK мгновенно.** Вся реальная обработка (вызов AI, запись в БД, отправка ответа клиенту) идёт асинхронно через очередь/воркер. Webhook-handler — это только: проверить подпись → положить событие в очередь → вернуть 200.
2. **Идемпотентность — на уровне БД, не на уровне кода.** Не пиши `if (!exists) { insert }` — это гонка состояний при параллельных ретраях. Полагайся на unique-индекс по `external_message_id` (см. скилл `database`) и обрабатывай ошибку конфликта как штатный случай ("уже обработано").
3. **Все вызовы Gemini — через один модуль.** `lib/server/ai/orchestrator.ts` (или аналог) — единственная точка, откуда вызывается Gemini API. Никогда не вызывай Gemini API напрямую из route handler'а или server action — иначе логирование (`ai_call_logs`) и retry-логика расползутся по проекту.
4. **Секреты только через переменные окружения / Supabase Vault.** Если видишь токен/ключ как строковый литерал в коде — это баг, даже если "временно для теста".
5. **Retry с экспоненциальной задержкой** на вызовы Gemini API (429) и на отправку сообщений в WhatsApp/Telegram (rate limits каналов).
6. **Валидация входных данных через Zod** на каждом webhook и API-роуте, до того как данные попадут в бизнес-логику.

## Источник правды по схеме и инструментам

Перед тем как добавлять новую таблицу или новый tool агента — открой `/docs/SPEC.md`, разделы 3 (схема БД) и 5 (инструменты). Не изобретай свои названия полей или новые tools "по аналогии" — расширяй именно то, что там описано, и обновляй SPEC.md, если добавляешь что-то новое.

## Структура (рекомендация, не догма)

```
/app/api/webhooks/whatsapp/route.ts   — приём, проверка подписи, постановка в очередь
/app/api/webhooks/telegram/route.ts   — то же для Telegram
/lib/server/ai/orchestrator.ts        — единая точка вызова Gemini + tool calling
/lib/server/queue/                     — обработка фоновых задач
/lib/server/channels/                  — отправка исходящих сообщений в WA/TG
```

## Логирование

Каждый вызов AI → строка в `ai_call_logs` (запрос, ответ, токены, latency). Каждая ошибка обработки webhook → лог с `conversation_id`/`lead_id`, чтобы можно было воспроизвести инцидент по конкретному диалогу.
